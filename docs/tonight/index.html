Your fork. A real contribution.

Each person will fork a real open-source project. The project is not chosen yet, so the repo link and sample-kit download will appear here once they are checked. Keep the original project's license and credit when you share your version.

The goal is a meaningful redesign or feature you can point to in a portfolio, with a repo link and a short narrated demo. A working GitHub Pages link is also a goal if the chosen app and timing support it.

Every task will have a prepared starting point. A slow or unfinished earlier task will not block the next one. Recording and narration can run while you do another task in separate files.

Controls, when you need them

Draft

We will practice these on a running task. Send Later and the exact workshop controls are still being checked.

Add to Queue
Your message waits until the current response finishes. It does not interrupt that response.
Steer with Message
Signals the current request to yield after the active tool finishes, then processes the new message. Use it for a correction while work is under way.
Stop
Stops the current request. It does not undo edits, commands or external actions that already completed. Stop and Send cancels the request and immediately sends your new message.
Send Later
The exact behavior and availability in the workshop setup are still being verified. We will explain it before using it; do not assume it means Add to Queue.
Attach a screenshot
The exact paste and attachment steps for the workshop setup are being checked. We will add them here once verified.

01

Make a quick, impactful redesign

Starting point

Your own fork of the selected open-source project and a working starting point. The project and exact screen are still being chosen.

Prompt
Read this project's instructions and use its existing code and components. Apply the redesign shown in my marked-up screenshot to this one screen. Keep the real interaction working and leave unrelated screens alone. Do not replace the app with a screenshot recreation. Check the result in the browser at desktop and phone width. Explain any missing dependency before asking to install it. Do not publish or push.

What you should see

A visible improvement in the real interface, in your own fork.

Checkpoint

Compare the screen with your markup and try the original interaction. What changed, and what still works?

If you're still waiting

Keep an unfinished attempt in its own branch or folder. The feature task will have a prepared starting point.

Go further

You make the mockup: capture the screen, draw arrows, mark it up, or crop and rearrange pieces. Attach that image to the next prompt. Manual markup is not Computer Use.

02

Add a more substantial feature

Starting point

A fresh working starting point in the same project. You do not need the redesign task to finish first.

Prompt
Help me add one useful feature to this existing project. First summarize the feature I described, the files you expect to change, and how we will check it. Use the existing architecture and real data flow. After I approve the scope, implement it and test the main path, an empty state and a failure case where relevant. Keep all unrelated behavior. Do not install, push or publish without my approval.

What you should see

A working feature, not just a new visual state. Its exact scope will be set with the chosen project.

Checkpoint

Try the feature yourself. Can you explain which part is your contribution and what checks actually ran?

If you're still waiting

Save the partial result and its open questions. Use the prepared baseline for visual alternatives instead of waiting.

Go further

Ask a second model to review the change, then reproduce its findings yourself.

03

Explore visual alternatives in parallel

Starting point

A saved baseline from the project, in separate working folders or worktrees. Check permissions before choosing worktrees.

Prompt
Explore exactly three meaningfully different layouts for this screen in the existing codebase. Keep the same content and working interaction. Give each direction its own folder or branch and do not let agents edit shared files. Preserve the baseline. Show the real results together for comparison and test them at desktop and phone width. Do not install, publish or merge anything without approval.

What you should see

Three real alternatives that differ in layout or hierarchy, not just color.

Checkpoint

Try the same action in each direction. Choose one decision you would keep and explain why.

If you're still waiting

If parallel sessions are unavailable, work through separate directions in turn. Label that as a sequential fallback.

Go further

Bring only the chosen result back to a clean branch, then check it again.

04

Make a narrated demo video

Starting point

A completed, saved interface or a prepared working version. Keep later edits away from the copy being recorded.

Prompt
Check whether you can make a short narrated recording of this working interface on my laptop. Explain the recording route, supported voice, any cost and any missing dependency before changing anything. After I approve the setup, record one complete interaction and save a playable video with narration. Play it back and check the result. Do not substitute screenshots, a silent clip or an animated webpage. Do not install or publish without asking.

What you should see

A playable narrated video from the real interface on your laptop. Start it, do another independent task, then come back to watch it.

Checkpoint

Open the file outside the chat. Can you see the complete interaction and hear the narration?

If you're still waiting

If recording or narration is unavailable, stop at the setup check and ask for help. A silent clip or screenshot sequence is not the planned result.

Go further

Add one sentence about the original project and what you changed, so the portfolio story gives proper credit.

05

Try Computer Use in a desktop app

Starting point

The agreed harmless task and app, with your own permissions. The exact example is still being chosen for Mac and Windows.

Prompt
Check whether Computer Use is available and explain the permissions needed for the agreed app. Do not enable anything. After I grant the required permissions and approve the task, work only in the agreed scratch material. Do not open personal documents, send, publish, purchase or change unrelated settings. Show me the actual result in the app and stop. If the task is not supported, tell me rather than claiming another tool did the same thing.

What you should see

A useful, harmless action completed in the real desktop app. The final task is still a draft.

Checkpoint

Inspect the app result and the scope of access. Did the agent do only the action you approved?

If you're still waiting

Leave permissions unchanged if the setup is unclear. A manual action is a fallback, not a Computer Use result.

Go further

Turn the permissions off afterward if you do not want the tool to keep access.

06

Set up Keep my taste current

Starting point

The draft plugin's automation template and references you explicitly choose. Its release and workshop steps are still being checked. The draft uses a Manual first trigger, then an explicitly chosen Run now before any optional schedule.

Prompt
Preview the Keep my taste current automation using only the references I choose. Show which files it would read, where it would write my personal taste skill, the proposed schedule, permissions, possible costs and how I can stop it. Do not read other files, install anything, enable the schedule or start a run yet. Let me review the setup and first-run plan.

What you should see

A reviewed setup for a personal taste skill, with an explicit choice before any run or recurring schedule.

Checkpoint

Can you see the selected sources, output and stop control? Installing the plugin alone must not enable an automation.

If you're still waiting

Keep the setup as a plan until the plugin, permission path and costs are checked. Do not create a replacement recurring job.

Go further

Taste and voice skills can shape later work. There is no separate live exercise writing them by hand.

07

Find themes in fictional interviews

Starting point

Clearly labeled fictional interview notes from the sample kit. No real participant data or private research is needed.

Prompt
Use only these fictional interview notes. Keep the output labeled as practice material. Group observations into at most three findings, each linked to the exact note that supports it. Keep contradictions and unanswered questions visible. Suggest one small next step for each finding. Do not invent quotes, participants or metrics, and do not claim this is evidence about real users.

What you should see

A short set of traceable findings and next steps, clearly labeled as fictional practice.

Checkpoint

Can you trace each finding to a supplied note? Are uncertainty and contradictions still visible?

If you're still waiting

If the notes are not ready, move to another task. Do not replace missing notes with invented customer evidence.

Go further

Choose one finding and draft a change you could later test with a real person.

08

Review your change and share your fork

Starting point

A saved change in your own fork. The pull request, Cloud and working-site steps depend on the final project and account setup.

Prompt
Review this fork's changes and explain what would become public. Keep the upstream license and credit. Prepare a small commit, a pull request description and a portfolio summary that clearly says what I changed. Check whether the real working app can be published with GitHub Pages; do not replace it with a fake static screen. Draft one bounded next task for Cloud. Do not push, publish, open a pull request, start Cloud work or merge until I explicitly approve each action.

What you should see

Your own repo link and a clear account of the redesign or feature. A working Pages link is a goal if the project and timing support it.

Checkpoint

Inspect the diff and public files. Does the portfolio description separate your changes from the upstream project?

If you're still waiting

Keep a local result and the publication plan if access or setup is incomplete. A prepared handoff is not a running Cloud task.

Go further

After approval, share the checked repo and working site, or hand one bounded task to Cloud. Never auto-merge.

09

Share it

Starting point

Your reviewed public fork and the checked static build for the chosen app. Guided-hour or free-work timing is still open.

Prompt
Prepare to publish my version on GitHub Pages. First check the real app works as static files, keep the original LICENSE and credit, and review what will be public. Show me the publishing source and any required build steps. Do not deploy until I approve. After an approved deployment, open the live URL in a fresh browser, test the main interaction and phone layout, then give me the verified live link beside my repo link.

What you should see

Publish your version on GitHub Pages, and share the live link with the repo link. This is a desired finish, not a promise that everyone will deploy during the guided hour.

Checkpoint

Open the live link without your sign-in and on your phone. Does the actual app work, and does your portfolio credit the upstream project?

If you're still waiting

Keep the repo and local result if the live build is not ready. Never present a screenshot recreation or broken deployment as the real working app.

Go further

Add the narrated demo and a short explanation of your redesign or feature beside both links.
